# ValiChord: Technical Architecture — Four-DNA Membrane Design

**Version:** 1.0 — March 2026
**Author:** Ceri John
**Status:** Infrastructure built and integration-tested
**Last checked against the code:** 2026-10-18 — Holochain 0.7.1 (`hdk =0.7.1`, `hdi =0.8.1`), after PR #47. Struct listings below are summaries; the source in `valichord/dnas/**` and `valichord/shared_types/` is authoritative.

---

## Overview

> 📐 **Diagrams drawn from the code (2026-10-18):** [the four DNAs and their cross-DNA calls](DIAGRAMS.md#1-the-four-dnas-and-who-talks-to-whom), [one round end to end](DIAGRAMS.md#2-one-validation-round-end-to-end), [what enforces what](DIAGRAMS.md#3-what-enforces-what), [the membranes](DIAGRAMS.md#4-the-membranes-who-may-join-each-dna). The older `4 DNA technical.png` image is partly out of date: prefer these where they differ.

ValiChord is implemented as four Holochain DNAs. Each DNA defines a distinct peer-to-peer network with its own entry types, link types, validation rules, and membrane boundary. The four DNAs run simultaneously on each participant's conductor, communicating via same-agent `call(OtherRole(...))` calls rather than cross-network messaging.

The architectural separation is not a design preference — it is the privacy and security model. Sensitive data is confined to single-agent private DNAs by structural impossibility of DHT propagation, not by policy. Until the reveal, only cryptographic hashes cross membrane boundaries. At reveal, each validator's attestation and the researcher's summary metrics are published on purpose; the dataset itself never is.

## DNA 1 — Researcher Repository

**Membrane:** Private. Single-agent. No DHT. No membrane proof required.

**Purpose:** Local storage of all research artefacts. Only two hashes leave this DNA: the dataset's SHA-256 `ExternalHash` (passed by the researcher into DNA 3's `ValidationRequest.data_hash`) and the result commitment hash (sent to DNA 3 by `lock_researcher_result`).

### Entry Types

Timestamps are not stored as fields: the Holochain action timestamp is authoritative.

```rust
// Private — never enters DHT
ResearchStudy {
    title:             String,
    discipline:        Discipline,
    institution:       String,
    abstract_text:     String,
    pre_registration_ref: Option<String>,   // DOI or URL of the pre-registration
}

// IMMUTABLE after creation — enforced in validate()
PreRegisteredProtocol {
    analysis_plan:        String,
    hypotheses:           Vec<String>,
    statistical_methods:  String,
}

// SHA-256 fingerprint of dataset at validation time
VerifiedDataSnapshot {
    data_hash:            ExternalHash,   // SHA-256, wrapped as a 39-byte HoloHash
    file_count:           u32,
    total_size_bytes:     u64,
}

// Wraps shared UndeclaredDeviation type as a private entry
// (linked from the study by StudyToDeviation)
DeclaredDeviation {
    deviation:   UndeclaredDeviation,
}
```

```rust
// THE RESEARCHER COMMIT — private, immutable after creation
// Generated by lock_researcher_result; never leaves this DNA
LockedResult {
    request_ref:        ExternalHash,
    metrics:            Vec<MetricResult>,  // structured per-metric results
    nonce:              Vec<u8>,            // 32-byte random nonce
    commitment_hash:    Vec<u8>,            // SHA-256(msgpack(metrics) || nonce)
    data_locality_mode: DataLocalityMode,   // Gdpr (default) | OpenAudit — see Data Locality Modes
}
```

### Link Types
```rust
StudyToProtocol
StudyToSnapshot
StudyToDeviation
RequestToLockedResult   // ExternalHash (request_ref) → LockedResult ActionHash
```

### Validation Rules
- `PreRegisteredProtocol`: all updates and deletes rejected — immutable after registration
- `LockedResult`: delete allowed in `Gdpr` mode, refused in `OpenAudit` mode (see Data Locality Modes)
- All other entries: only original author may update or delete
- No membrane proof check — single-agent DNA, no joining credential required

### Key Coordinator Functions
- `register_study`, `register_protocol`, `take_data_snapshot`, `declare_deviation`
- `compute_data_hash(data: Vec<u8>) → ExternalHash` — SHA-256 via `sha2` crate, returns `ExternalHash::from_raw_32()`
- `lock_researcher_result` — generates 32-byte nonce, computes commitment hash, writes `LockedResult` (private), then calls DNA 3 `publish_researcher_commitment` to put only the hash on the shared DHT

### Engineering Notes
- All entry types declared `visibility = "private"` in `EntryTypes` enum
- No `init()` capability grants needed — single-agent, all calls run under author grant automatically
- `compute_data_hash` is the only outward-facing function in the sense that its output (an `ExternalHash`) is what travels to DNA 3

## DNA 2 — Validator Workspace

**Membrane:** Private. Single-agent. No DHT. No membrane proof required.

**Purpose:** The commit phase of the blind commit-reveal protocol. Each validator runs one instance of this DNA. The private assessment is sealed here and never leaves. The only outward communication is a `call(OtherRole("attestation"))` fired from `post_commit` to notify DNA 3 that a commitment has been made.

### Entry Types

```rust
ValidationTask {
    request_ref:       ExternalHash,
    discipline:        Discipline,
    deadline_secs:     u64,
    validation_focus:  ValidationFocus,   // ComputationalReproducibility | PreCommitmentAdherence | MethodologicalReview
    time_cap_secs:     u64,
    compensation_tier: CompensationTier,
}

// THE COMMIT — private, immutable after creation
// (sealing time comes from the action timestamp, not a field)
ValidatorPrivateAttestation {
    request_ref:             ExternalHash,
    outcome:                 AttestationOutcome,
    outcome_summary:         OutcomeSummary,
    time_invested_secs:      u64,
    time_breakdown:          TimeBreakdown,
    deviation_flags:         Vec<UndeclaredDeviation>,
    computational_resources: ComputationalResources,
    confidence:              AttestationConfidence,
    discipline:              Discipline,
    nonce:                   Vec<u8>,          // 32 random bytes, generated at seal time
    commitment_hash:         Vec<u8>,          // SHA-256(msgpack(ValidationAttestation) || nonce)
    reproduction_bundle_hash: Option<Vec<u8>>, // content_hash of the validator's own bundle, if any
}

// A validator's deliberate decision not to take part — immutable
DeliberateAbstention {
    request_ref: ExternalHash,
    reason:      Option<String>,
}
```

### Link Types
```rust
TaskToPrivateAttestation
RequestToAbstention
```

### Validation Rules
- `ValidatorPrivateAttestation` and `DeliberateAbstention`: all updates and deletes rejected — immutable after creation
- `seal_private_attestation` (coordinator) refuses a second seal for the same task, so a validator cannot re-seal after seeing others' reveals
- All other entries: only original author may update or delete

### post_commit — Critical Path

```rust
#[hdk_extern(infallible)]
pub fn post_commit(committed_actions: Vec<SignedActionHashed>) {
    // Detects ValidatorPrivateAttestation creation
    // Calls DNA 3 via call(OtherRole("attestation"),
    //   "attestation_coordinator",
    //   "notify_commitment_sealed",
    //   CommitmentSealedInput { request_ref, commitment_hash })
    // Only the public identifier and the opaque hash cross — never content.
}
```

**Important constraint:** The target attestation cell must be initialised (i.e. `init()` must have run) before `post_commit` fires. If `post_commit` triggers `init()` in the target cell for the first time, the conductor serialises cell operations and deadlocks. In production, the UI layer initialises all cells on startup. In tests, a warm-up read call is required before `seal_private_attestation`.

## DNA 3 — Attestation

**Membrane:** Shared DHT. Credentialed joining. Membrane proof required.

**Purpose:** All inter-validator coordination. Manages the full commit-reveal protocol. The credentialed membrane ensures only institutionally verified validators participate. This is the most complex DNA — it contains the phase transition logic, the commitment detection mechanism, and the public attestation record.

### DNA Properties

```rust
#[dna_properties]
pub struct DnaProperties {
    pub authorized_joining_certificate_issuer: String, // base64 AgentPubKey (uhCAk…); "" = dev bypass
    pub ai_validator_issuer: String,   // signs AI-validator certificates; "" = use the key above
    pub discipline:          String,
    pub minimum_validators:  u32,      // a FLOOR for num_validators_required, not the quorum target
    pub min_claim_timeout_secs: u64,   // before reclaim_abandoned_claim may free a slot
}
```

Properties are baked into the DNA hash at deployment — immutable per network instance. The quorum for a round is the study's own `num_validators_required` (1–255, set per `ValidationRequest`); `validate()` rejects a request whose number is below `minimum_validators`.

### Commit-Reveal Protocol Flow

```
DNA 2 post_commit
    → call(OtherRole("attestation"), "notify_commitment_sealed", request_ref)
        → write CommitmentAnchor to DHT
        → create_link(commit_path, anchor_hash, RequestToCommitment)
        → count CommitmentAnchors via get_links(commit_path)
        → if count >= the study's num_validators_required:
            → write PhaseMarker(RevealOpen)
            → create_link(phase_path, marker_hash, RequestToPhaseMarker)
            → emit_signal(Signal::RevealOpen) — UI notification only, NOT a protocol gate
            → send_remote_signal(RevealOpenWire) to all other committed validators

Validator polls get_current_phase(request_ref)
    → get_links(phase_path, RequestToPhaseMarker)
    → returns Option<ValidationPhase>
    → None = commit phase still open
    → Some(RevealOpen) = reveal window open

Validator calls submit_attestation(attestation)
    → verify SHA-256(msgpack(attestation) || nonce) == the validator's CommitmentAnchor hash
    → copy num_validators_required and the request's creation time onto the attestation
    → create_entry(ValidationAttestation) — required_validations = 7
    → create_link(agent, hash, ValidatorToAttestation)
    → call_governance_fire_and_forget("check_and_create_harmony_record", request_ref)
        → Ok  → round finalised (HarmonyRecord written to governance DHT)
        → Err → emit_signal(Signal::FinalizationFailed) — UI prompted to retry
```

**Phase transition is DHT-poll-driven, not signal-driven.** Signals are send-and-forget and cannot be relied upon for protocol state transitions. `get_current_phase()` is the authoritative source of phase state.

### Signals emitted by DNA 3

All signals use `#[serde(tag = "type", content = "content")]` (adjacent-tag). The msgpack payload delivered to the AppWebsocket is `{ type: "<Variant>", content: { ... } }`.

| Signal variant | When emitted | Scope |
|---|---|---|
| `RevealOpen { request_ref }` | All required validators have committed; reveal window open | Local + remote (send_remote_signal to other committed validators) |
| `FinalizationFailed { request_ref }` | `submit_attestation` succeeded but the governance cross-DNA call failed | Local only |

`RevealOpen` is a best-effort notification — the UI must always verify via `get_current_phase()`. `FinalizationFailed` signals that the attestation is safely written but the round needs manual recovery (`force_finalize_round` or waiting for another validator's reveal to retry).

### Validation Rules (validate callback)

Immutability guards **must** precede the generic update arm — Rust match ordering is the enforcement mechanism:

```rust
// GUARDED ARMS FIRST
FlatOp::Update(OpUpdate::Entry {
    app_entry: EntryTypes::ValidationAttestation(_), ..
}) => Invalid("immutable")

FlatOp::Update(OpUpdate::Entry {
    app_entry: EntryTypes::CommitmentAnchor(_), ..
}) => Invalid("immutable")

FlatOp::Update(OpUpdate::Entry {
    app_entry: EntryTypes::PhaseMarker(_), ..
}) => Invalid("immutable")

// GENERIC ARM AFTER
FlatOp::Update(OpUpdate::Entry { action, .. }) => {
    // author check only
}
```

> **Variant names are the 0.7 ones** (`hdi 0.8.x`; `0.8.1` since Holochain 0.7.1): `FlatOp::Update`, not 0.6's
> `FlatOp::RegisterUpdate`. The rename is cosmetic; the ordering rule above is not, and
> a mechanical reflow that reorders these arms disables immutability with no compile
> error. Ordering is checked mechanically and proven at runtime by the tripwire suite
> (`sweettest_integration/tests/immutability_tripwire.rs`) — see `Holochain_complete.md` §44.2.

**Delete guards are a separate claim from update guards, and need their own tests.** Sixteen
"cannot be deleted" guards sat with no coverage that could fail until 2026-08-01; eight tests
that appeared to cover them were calling zome functions that had never been written and passed
on *"function not found"*. Five delete tripwires now mirror the five update ones. A guard's
arm being in the right place and the guard actually rejecting the op are different claims.

### Membrane Proof

**Peer-enforced since PR #47 (merged 2026-10-18).** One function, `attestation_integrity::check_joining_certificate`, does the full check (parse the `JoiningCertificate`, pick the issuer key for its validator type, Ed25519 `verify_signature` over `joining agent's 39-byte key || certificate meta bytes`). It runs in three places:

1. **`validate()`, on the `AgentValidationPkg` op — every peer.** This is the security property: a modified hApp cannot skip it.
2. `genesis_self_check` — the joining agent, before joining. Turns a bad credential into a clear install error.
3. coordinator `init()` — the joining agent, on first zome call. Defence in depth.

Only the first protects anything; the other two fail fast and legibly. Before #47 the integrity zome checked only that the proof was at least 64 bytes, on the mistaken belief that `verify_signature` is not available in integrity zomes (it is). Human certificates are checked against `authorized_joining_certificate_issuer`; AI certificates against `ai_validator_issuer` if set. An empty `authorized_joining_certificate_issuer` switches the whole credential system off for dev/test mode.

The same certificate also binds a validator's tier: a `ValidatorProfile` carries its author's `joining_certificate`, and every peer rejects a profile whose `certification_tier` differs from what that certificate grants.

### Capability Grants (init)

Read functions only are `Unrestricted` — accessible via HTTP Gateway without a capability token. Write functions (`notify_commitment_sealed`, `submit_attestation`) are **not** listed — they run under author grant via `call(OtherRole(...))`.

## DNA 4 — Governance & Harmony Records

**Membrane:** Public DHT. Open read. No membrane proof required for joining. Writes are checked in `validate()`: `ValidatorReputation` and `GovernanceDecision` by a DNA-property key; `HarmonyRecord` and `ReproducibilityBadge` by the evidence they carry (see below).

**Purpose:** The public face of ValiChord. Permanent, tamper-evident validation outcomes. HTTP Gateway target — designed to be queryable by journals, funders, and the public without running a Holochain node. (`hc-http-gw` is not deployed today; the public demo serves records through its Node bridges — see `PROJECT_STATUS.md`.)

### DNA Properties

```rust
#[dna_properties]
pub struct DnaProperties {
    pub system_coordinator_key: String, // may write ValidatorReputation and GovernanceDecision
    pub min_attestations_for_finalization: u32, // 0 is treated as 1
    pub round_timeout_secs: u64,         // default 604800 (7 days)
}
```

In test/dev mode, an empty string for `system_coordinator_key` bypasses the key check. In production, a real `AgentPubKey` base58 string is baked in at deployment.

> **Note:** An earlier design included a second key `harmony_record_creator_key` that restricted `HarmonyRecord` and `ReproducibilityBadge` writes to a single trusted agent. This was removed. `HarmonyRecord` creation is now **participatory** — any validator who appears in `participating_validators` of the round may trigger finalisation by calling `check_and_create_harmony_record`. The integrity zome enforces that `action.author ∈ participating_validators` rather than checking a fixed key — and, since PR #47, that every listed validator's signed attestation is carried in the record and checks out (see Validation Rules). This removes a single-point-of-failure from round finalisation and is more consistent with Holochain's agent-centric model.

### Entry Types


### Badge Thresholds

From `evaluate_badge` (`shared_types`) and its integrity-zome mirror `badge_ceiling`. Validator count is the raw number of participating validators. **These numbers are placeholders, to be calibrated with real data — they are not statistically justified.**

| Badge | Validator Count | Agreement Requirement |
|---|---|---|
| GoldReproducible | ≥ 7 | ExactMatch |
| SilverReproducible | ≥ 5 | ExactMatch or WithinTolerance |
| BronzeReproducible | ≥ 3 | ExactMatch, WithinTolerance or DirectionalMatch |
| FailedReproduction | ≥ 3 | Divergent or UnableToAssess |

Agreement levels come from `derive_agreement_level`: ExactMatch if ≥ 90% fully reproduced; WithinTolerance if ≥ 70% reproduced or partially reproduced; DirectionalMatch if ≥ 50%; Divergent if any; otherwise UnableToAssess. These cutoffs are placeholders too.

> **Phase 0 caveat — badge tier reflects participant count and agreement level only.** Validator tiers play no part in the badge calculation: `evaluate_badge` takes the raw count. Human validators' tiers do not progress in production either: `_update_reputation_internal` runs only on a dev network or on the `system_coordinator_key` holder's own conductor, and who writes `ValidatorReputation` in production is undecided. (AI validators' tiers are set by their certificate issuer, and peers check this since #47.) A Gold badge means seven validators independently agreed; it does not mean seven validators with a verified track record agreed. All public descriptions of ValiChord badges must reflect this.

> **Second caveat — every badge tier needs `DirectionalMatch` or better, so a set-valued claim can rarely earn one.** See Phase 0 limitation 5 below: for results that are a *set* rather than a value (which variables are in a model, a ranking, a list of detected items), honest independent validators routinely return different sets while agreeing completely on what the data determined. Such a round lands in `Divergent` and is therefore eligible only for `FailedReproduction` — the exact inversion of what happened. Do not describe the badge ladder as covering all claim types until the agreement vocabulary is extended.

### Validation Rules

`HarmonyRecord` and `ReproducibilityBadge` writes are now participatory — no fixed creator key:

```rust
// HarmonyRecord, ReproducibilityBadge
if !record.participating_validators.contains(&action.author()) {
    return Invalid("Author must be a participating validator")
}

// ValidatorReputation, GovernanceDecision (skipped when the key is "")
if action.author().to_string() != props.system_coordinator_key {
    return Invalid("Only system_coordinator_key may write")
}
```

**HarmonyRecord content is checked by every peer (PR #47, `check_attestation_evidence`).** `validate()` cannot call across to DNA 3, but it does not need to: the record carries, for each listed validator, the signed `Create` action that wrote their `ValidationAttestation`, plus the attestation itself. Peers check that:

- there is one piece of evidence per listed validator, no duplicates, and at least `min_attestations_for_finalization`;
- each signature verifies against the listed key, over an action whose entry hash is the carried attestation's hash, for this `request_ref`;
- `outcome`, `agreement_level`, `validation_duration_secs` and `discipline` are exactly what the carried attestations produce;
- `validators_requested` matches the cohort size every attestation states (checked against the `ValidationRequest` by DNA 3's peers), and a record with fewer attestations than requested is only valid after `round_timeout_secs`.

What this does **not** prove: that the attestations were also published on DNA 3; which subset was chosen after a timeout (though the record shows "k of n"); or anything about validators who collude and each sign a false attestation. The timeout check also reads the record's own timestamp, which its author asserts.

`ReproducibilityBadge`: `harmony_record_ref` must point to a HarmonyRecord for the same study, and `badge_type` must not exceed the ceiling the record's count and agreement level allow.

All entry types block deletes. `ValidatorReputation` allows updates (coordinator key enforced). `HarmonyRecord`, `ReproducibilityBadge`, and `GovernanceDecision` are fully immutable.

### check_and_create_harmony_record

Called from DNA 3's `submit_attestation` (via `call_governance_fire_and_forget`; DNA 3's `post_commit` is a no-op). Idempotent — checks for existing `HarmonyRecord` before creating. Calls back into DNA 3 via `call(OtherRole("attestation"), "get_attestations_for_request")` and `get_num_validators_required` to read attestations and the cohort size, and writes nothing until every expected attestation is present. Short rounds are closed by `force_finalize_round` instead (see Phase 0 limitation 6).

**Re-entrancy warning:** governance must call attestation **read** functions only. On the automatic path DNA 3 is still executing `submit_attestation`, so a back-call can fail; the code expects this for badge issuance (`try_issue_badge`) and repairs it on the next call via `issue_badge_if_missing`.

## Cross-DNA Communication Pattern

Same-agent `call()` is the only permitted cross-DNA communication. `call_remote()` cannot cross DNA network boundaries.

```
DNA 1 lock_researcher_result
    → call(OtherRole("attestation"), publish_researcher_commitment)   // write (hash only)

DNA 2 post_commit
    → call(OtherRole("attestation"), notify_commitment_sealed)   // write

DNA 3 submit_attestation
    → call(OtherRole("governance"), check_and_create_harmony_record)   // write

DNA 4 check_and_create_harmony_record / force_finalize_round
    → call(OtherRole("attestation"), get_attestations_for_request, …)   // read only
```

All these arrows run on the same agent's conductor. The governance call from DNA 3 and the attestation read from DNA 4 must not form a cycle with any pending write operation on either cell — see deadlock warning above.

## Known Limitations — Phase 0

These are not bugs — they are deliberate Phase 0 boundaries that affect how external parties should interpret ValiChord outputs until Phase 1 resolves them.

**1. Validator experience is not tracked in production.** `_update_reputation_internal` (DNA 4) runs only when `system_coordinator_key` is empty (dev) or on the key-holder's own conductor; who that is in production is undecided. A human validator's `CertificationTier` therefore stays `Provisional` in production regardless of completed rounds. (An AI validator's tier is whatever its certificate issuer granted, checked by peers since #47.) Badge tiers reflect participant count and agreement level only, not validator track record. Phase 1 wires in a trusted `update_validator_reputation` caller. See the Phase 0 caveat in the Badge Thresholds section above.

**2. Device key continuity is unresolved.** `ValidatorReputation` and `ValidatorProfile` are keyed by device `AgentPubKey`. A validator who rotates their key (new device, key compromise) starts with a clean reputation record. The `person_key: Option<AgentPubKey>` field exists in both structs to hold a future stable person-level identity from Flowsta or Deepkey, but population and aggregation logic are Phase 1 work — the field is `None` for all current records. Until Phase 1, a validator's reputation history does not survive a device change.

**3. There is no validator assignment engine.** The old `select_validators()` stub was removed as dead code in March 2026. Validators self-assign by claiming studies (`claim_study`); `validate()` enforces the same-institution conflict-of-interest rule and the coordinator enforces capacity. A future random pool-draw for AI validators is sketched in comments in `attestation_coordinator`. Wider conflict-of-interest detection (beyond same institution), institutional balance, and randomisation are Phase 1 work.

**4. Private commit-reveal state is not recoverable after total machine loss.** The commit-reveal nonce is a random 32 bytes (`random_bytes(32)`), stored only in a **private** entry — `LockedResult` (DNA 1) for the researcher, `ValidatorPrivateAttestation` (DNA 2) for the validator — and it is required to reveal (reveal recomputes `SHA-256(msgpack(content) || nonce)` against the public commitment). An agent who loses their machine *between committing and revealing* loses the nonce and can never complete that reveal. Holochain's 0.7 **Source Chain Restore** does not close this: DNA 1 and DNA 2 are single-agent private DNAs with no peers to restore from (and `restore_chain_quorum` defaults to 2), and restore would not carry private entry *content* in any case. The durability of pre-reveal sealed state is therefore inherently a client-side concern, and it sits downstream of device-key continuity (limitation 2 — if the keystore is lost, restore is moot and the agent is new).

*This is a liveness edge, not a safety one:* no record is corrupted, blinding is intact, and the protocol already routes around a non-revealing participant via the existing timeout path (`release_claim` / `reclaim_abandoned_claim` / `force_finalize_round` / the hourly finalisation sweep) — a restored-but-nonce-less participant is simply an abandoned one. **Plan (decided 2026-07-19): accept-and-document for Phase 0/1** (nothing to build; we are on 0.6.2 and will not migrate until 0.7 is stable). *[Since then: migrated to 0.7.0 on 2026-08-03 and 0.7.1 on 2026-10-17. Source-chain restore in 0.7.1 recovers public state only.]* At the 0.7 migration, handle the new `AppStatus::AwaitingRestore`/`Unrecoverable` states and, if a validator "restore" is ever exposed in the UI, warn that an in-flight sealed round should be left to time out rather than resumed. **Deferred hardening (Phase 2, only on real demand):** a strict encrypt-to-self durable backup of `{content + nonce}` reusing the Open-Audit `x_salsa20_poly1305` mechanism (see Data Locality Modes) — gated on an actual high-stakes deployment needing mid-round crash recovery, not built on spec.

**5. The agreement vocabulary assumes a point-valued result, and breaks on set-valued claims.** `AgreementLevel` is derived by comparing validators' outcomes for equality (`ExactMatch` when the full-reproduced rate is unanimous, degrading through `WithinTolerance` to `Divergent`). That is the right shape for "the metric was 0.9158". It is the wrong shape when the claim itself is a **set** — which variables a model selected, a ranking, a list of detected items — because two honest validators working from independent resamples will routinely return *different sets while agreeing completely on everything the data determined*.

Consequence: such a round reports total disagreement among validators who did not disagree, and (per the second Badge Thresholds caveat above) is eligible only for `FailedReproduction`. **This is a semantics gap, not a bug** — no code is wrong; the vocabulary simply has no term for "agreed on what was determined, differed on what was not."

*Evidence — simulated and synthetic, see the caveats below.* `valichord_attestation/examples/feature_selection_stability/REPORT.md`, on branch `research/feature-selection-stability` (2026-07-27), ran a five-validator commit-reveal round over L1 feature selection with correlated feature blocks (ρ ≈ 0.95). Result: **5 distinct supports across 5 validators**, yet **all three blocks selected 5/5** — the true member of each block held 100% while its correlated partners scattered at 24–33%. Exact match reads that as complete divergence; a frequency-based reading reads it as unanimity plus a correctly-identified ambiguity.

*Direction, not a decision.* The likely fix is a frequency/threshold-based agreement variant for set-valued claims, counting at the level of what the data determines rather than the raw set. The threshold is deliberately left unset — the same reason the report declines to pick one. **Caveats before acting:** the parties in that experiment were simulated (six processes in one script, no conductor, no DHT), the data was synthetic, and counting at group level is prior art rather than our idea (Faletto & Bien, *Cluster Stability Selection*, arXiv:2201.00494, 2022; earlier group-level selection proportions in Kirk et al. 2010, Alexander & Lange 2011, Gauraha 2016). Treat this as a well-motivated design input, not a validated result — and note the unit of counting is domain-specific, so a protocol-level fix needs more than one worked example.

**6. Round finalisation infers "abandoned" from age alone, and can permanently understate participation.** *(Largely fixed — see the update note below; this paragraph describes the code as it was on 2026-08-02.)* `force_finalize_round` (DNA 4) closes a round when `elapsed_secs >= round_timeout_secs`, measured from the **ValidationRequest's** action timestamp. Its other gates are idempotency, a non-empty attestation set, `min_attestations_for_finalization` (which **silently coerces 0 → 1**), a `request_ref` match and a warrant filter. **There is no check for outstanding claims** — nothing asks whether validators are still working. `sweep_timed_out_rounds`, scheduled hourly in `init()` on every conductor, calls it for every pending study, so this runs automatically and unattended.

> **Update (checked against code 2026-10-18).** Two of the fixes below have since been built. (1) **Liveness gate** (2026-08-02, commit `fd56cc4`): `force_finalize_round` no longer closes a round while any validator still holds a live claim — see step "3b. LIVENESS GATE" in `governance_coordinator`. (2) **Honest record**: `HarmonyRecord.validators_requested` records the cohort asked for, and since PR #47 peers check it against every carried attestation, so an early close reads as "k of n". **Still open:** badges are computed from the number who reported, not from the pair, so a 5-of-7 record can still earn Silver. The text below is the original analysis from 2026-08-02.

Consequence: a **slow-but-healthy round is indistinguishable from an abandoned one**. Reproduction legitimately takes days or weeks; if the timeout is 7 days and a validator needs 9, the round is closed with whoever has revealed so far. A HarmonyRecord is immutable, so the late attestations are orphaned permanently, participation is understated forever, and the badge tier derived from that count is wrong (a genuine 7/7 becomes Bronze). **For a system whose only output is a permanent public record of how many independent parties reproduced a result, this is a record that states something false.**

*Discovered 2026-08-02* while diagnosing the long-running badge flake. The sweettest DNA properties set `round_timeout_secs: 0` **and** `min_attestations_for_finalization: 0`, opening both gates, so any multi-validator test still in flight when the wall clock crossed the top of an hour had its round force-finalised with a partial set. That produced `gold_badge_issued_with_seven_validators`'s `left: 5, right: 7`, and explains why the failure moved between tests and why docs-only commits flipped it. The test-side fix (long default timeout, `round_timeout_secs: 0` now opt-in) does **not** address the design issue described here.

*Design conclusions reached in discussion, not yet built:*

- **An idle timeout does NOT fix this, despite appearing to.** Measuring "time since the last DHT event for this round" fails on the exact case it is meant to protect: a validator claims a slot, then does the reproduction work — days of it — generating **no DHT activity at all**, and only returns to commit and reveal. An idle clock would read a round of quietly-working validators as empty.
- **The live claim is the real liveness signal.** A `StudyClaim` is a validator asserting "I hold this slot"; it stays live until they reveal or someone explicitly releases it. So the gate should be: **do not finalise while any live claim remains.** `get_claims_for_request` already returns exactly the live set (releases filtered out), so this needs no new zome function and is **coordinator-only** — it hot-swaps with zero DNA-hash change. The "how long before we declare someone absent" decision then lives where it belongs, in `reclaim_abandoned_claim` and its `min_claim_timeout_secs`, as a deliberate, auditable act rather than a clock's inference.
- **Some validators can never return.** A validator who loses their machine mid-round loses the sealed nonce with it and can never complete that reveal (limitation 4). So the protocol *must* be able to close such a round; waiting indefinitely is not a design, and the question is not only "how long do we wait" but "what do we write down when we stop".
- **Asking the missing validator is possible, but must be a noticeboard, not a message.** Signals are fire-and-forget with no delivery receipt and an absent agent receives nothing. The workable form is a durable challenge entry on the DHT plus a heartbeat reply, read whenever that agent's conductor next runs. Note this makes "multiple attempts" unnecessary — one persistent notice beats N ephemeral pings; what is wanted is a generous *window*. ⚠️ **An automatic heartbeat proves only that a machine is switched on, not that a human is working**, so it needs bounding (a capped number of extensions, or a second absolute deadline) or it merely replaces a clock that fires too eagerly with one that never fires.
- **The strongest fix may be to make the record honest instead of complete.** The damage is not that a round closes early; it is that the record then *misstates* what happened. If `HarmonyRecord` carried **both** the requested cohort size and the number who reported, an early close would be plainly incomplete rather than quietly false, and the badge could key off the pair (3-of-7 simply is not Gold). That removes most of the danger from the timing rules and lets them be generous and simple. This is integrity-level, so it should ride a DNA-hash break rather than pay for one of its own — see the Open Audit note about settling entry shapes before the next break.

## Data Locality Modes

The blind commit-reveal protocol, phase transitions, and Harmony Record are identical in both modes. Only where the dataset lives changes. The mode is set at submission and cannot be changed after the commitment is posted.

### GDPR Mode (default)

The researcher's dataset stays in DNA 1 (Researcher Repository). `VerifiedDataSnapshot.data_hash` (SHA-256 of the dataset) is passed to DNA 3 as `ValidationRequest.data_hash`. The data never enters any shared DHT.

Third parties can independently audit the entire process — the hash chain, phase transitions, attestations, and Harmony Record are all on the DNA 3 and DNA 4 DHTs. They cannot re-verify the underlying data without access to the researcher's private DNA.

**Required for:** patient data, clinical trial data, or any dataset with GDPR or data-sharing restrictions.

### Open Audit Mode

The researcher generates an X25519 keypair for the study. At submission, the dataset is encrypted using Holochain's native `x_salsa20_poly1305_encrypt` (X25519 key exchange + XSalsa20-Poly1305 AEAD) and stored on the DNA 3 DHT as an `EncryptedDataset` entry. The commitment hash is computed from the plaintext as before — encryption does not affect the protocol.

After reveal, the researcher publishes the X25519 private key. This travels as a new field on `ResearcherReveal` (or as a separate `DatasetDecryptionKey` entry linked to the request).

Any third party can now independently verify: retrieve `EncryptedDataset` from DHT → decrypt with the published key → SHA-256 the plaintext → compare against `ValidationRequest.data_hash`. The Harmony Record is fully self-verifying without trusting ValiChord or the researcher's private system.

**Key management:** The X25519 keypair is generated per-study (not the agent's signing key). The private half is held in DNA 1 alongside the `VerifiedDataSnapshot`; the public half is included in `ValidationRequest` so the ciphertext can be associated with the right key. At reveal, the private half is published.

**Constraints:**
- The decryption key, once published in the Harmony Record, is irrevocable. Open audit mode is a permanent commitment to post-reveal public access.
- GDPR-sensitive datasets must use GDPR mode regardless of researcher preference — publishing a decryption key permanently defeats erasure rights.
- `EncryptedDataset` entry type, X25519 key generation in DNA 1, decryption key field on `ResearcherReveal`, and submission-time mode selector are Phase 1 work — **except the mode field itself and its erasure consequence, which are built; see below.**

### What is built today (2026-08-01)

**Only the erasure consequence.** `DataLocalityMode` is a real two-variant enum in
`shared_types` (`Gdpr` | `OpenAudit`, defaulting to `Gdpr`), carried as
`LockedResult.data_locality_mode` in DNA 1 and fixed at lock time. The DNA 1 delete guard reads
it off the record it is already fetching and branches:

| Mode | `LockedResult` delete | Why |
|---|---|---|
| `Gdpr` | **allowed** | Guarding it would remove the erasure right the mode exists to protect, and buys nothing — the binding commitment is `ResearcherResultCommitment` on DNA 3, already public and immutable. Deleting a `LockedResult` destroys only the researcher's own ability to reveal: the same outcome as declining to reveal, which the protocol already handles as an abandoned round. |
| `OpenAudit` | **refused** | The mode *is* a permanent commitment to post-reveal public access. Erasing the sealed material afterwards contradicts the promise. |

Two notes on why it is shaped this way:

- **The mode lives on the entry, not on the `ValidationRequest`.** `validate()` is deterministic
  and cannot call across to DNA 3, so the guard cannot look the mode up — it must be handed it.
- **It was taken now on purpose.** This is an *integrity-level* field: adding it later would cost
  a second DNA-hash break, and the 0.7 migration is already paying for one. Everything in
  production today is `Gdpr`; the `OpenAudit` branch is groundwork with no way to reach it yet.

Feasibility was established by accident the same day: `PreRegisteredProtocol` is
`visibility = "private"` and its delete guard demonstrably works, proving `validate()` in this
all-private DNA can fetch and deserialise the entry it is guarding. Without that, none of this
would have been possible.

## Shared Types

All cross-DNA types live in `valichord/shared_types/` — a pure `rlib` crate imported by all four DNAs. This avoids the `cdylib` duplicate-symbol error that occurs when types are defined in an integrity zome (compiled as `cdylib`) and re-exported across crates.

Key shared types: `Discipline`, `AttestationOutcome`, `AttestationConfidence`, `ComputationalResources`, `TimeBreakdown`, `UndeclaredDeviation`, `ValidationPhase`, `OutcomeSummary`, `MetricResult`, `AgreementLevel`, `CertificationTier`, `DataLocalityMode`, `ValidatorType`, `ValidatorAgentType`, `JoiningCertificate`, `ValidationAttestation`, `BadgeType`, and the pure functions `discipline_tag()`, `derive_majority_outcome()`, `derive_agreement_level()` and `evaluate_badge()`.
